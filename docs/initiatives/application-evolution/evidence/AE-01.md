# Shared approval foundation: local evidence

Two distinct applications consume one versioned foundation. ApprovalDesk records purchase
orders; ExpenseDesk records reimbursements. Changing the shared approval limit changes both
applications without editing their business source. This is a local maintainer/agent construction
exercise with automated checks, not an independent adoption or productivity study.

The [workspace](../../../../samples/applications/SharedApprovals/README.md) contains the implementation.
The [machine receipt](AE-01.receipt.json) identifies the input file hashes, resolved package graphs,
package hashes, individual assertions, and the local Core repair. It is the authority for the
completed run's exact check count. The [live ledger](../PROGRESS.md) owns execution status.
The final run passed all 163 assertions. Its application baseline is commit
`157f9053ec10cce86154c433be119f9a2d624e0e`.

## Reproduce the historical run

These commands belong to baseline `157f9053ec10cce86154c433be119f9a2d624e0e`, with .NET 10
SDK, PowerShell 7, Git, and access to nuget.org. For current setup and the released dependency
path, use the [published-package follow-up](AE-01a.md).

```powershell
pwsh samples/applications/SharedApprovals/prepare-framework.ps1
pwsh samples/applications/SharedApprovals/verify.ps1
```

Preparation packs the Core repair locally at its computed version. The verifier copies the
sample into an isolated fixture, creates controlled Git history, packs the two foundation
versions into a local feed, and uses a fresh NuGet cache. All six application builds consume
the foundation as an actual PackageReference. Ordinary authoring uses a ProjectReference.

The fixture's 1.0.1 and 1.0.2 are computed experimental versions, not public releases. The sole
executable policy change is `ApprovalPolicyOptions.MaximumApprovalAmount`, from USD 1,000 to
USD 500. The packaged README changes alongside it and is checked against the corresponding
limit. Consumer source and the earlier package's bytes remain unchanged.

Each run retains `receipt.json`, tool/host logs, facts, MCP responses, packages, and SQLite files
under `artifacts/application-evolution/<run-id>`. The checked-in receipt removes the workstation's
absolute package path; the full local original retains it. Failed runs are retained too.

## Observed behavior

| Probe | Original foundation | Updated foundation | Isolated rollback |
|---|---|---|---|
| Shared limit shown by both applications | USD 1,000 | USD 500 | USD 1,000 |
| Approve and finish a USD 250 request | Pass | Pass | Pass |
| Approve a new USD 750 request | Allowed | Rejected; remains pending | Allowed |
| Ordinary HTTP upsert bypasses the tighter rule | — | Rejected | — |
| MCP approval exactly at the current limit | Allowed and persisted | Allowed and persisted | Allowed and persisted |
| MCP approval one dollar above the current limit | Corrective rejection; no write | Corrective rejection; no write | Corrective rejection; no write |
| Edit an approved amount or insert an approved row | Rejected | Rejected | Rejected |
| Repeat order/reimbursement action | Same recorded result | Same recorded result | Same recorded result |

The updated hosts reuse the original SQLite files and retain prior approved records and completed
business outcomes. A USD 750 request approved before the update can still finish its order or
reimbursement after the limit tightens; both consumers passed that continuation check.
Rollback uses separate data: it proves earlier policy behavior, not reversal
of decisions. Anonymous HTTP removal returns 401 under the declared access rule; that probe does
not claim to exercise the lifecycle removal handler.

Runtime facts are complete and identify SQLite activation through `Example.Approvals.Foundation`
and host-composed Entity lifecycle handlers. Persisted records are read back and actual SQLite
files exist. This proves the selected local provider path, not parity with other providers.

Both normal `dotnet run` paths were also exercised in Chrome: purchase submission → approval →
recorded order, and expense submission → approval → recorded reimbursement. Both displayed the
USD 500 shared limit. Desktop screenshots were inspected; no browser errors were observed after
the asset fix. Screenshots remain under `artifacts/application-evolution/browser/`.

## What the experiment found

Published `Sylin.Koan.Core` 1.0.33 wrote the ordinary private foundation's identity into the
activation manifest and then rejected that identity at startup. The Core repair in commit
`6e2aafc56` aligns runtime validation with the existing writer's identity grammar. It preserves
malformed-input rejection and dependency reachability; 35 focused parser/activation tests passed.

The application proof therefore uses locally packed Core 1.0.34, plus published App 1.0.22,
SQLite connector 1.0.29, and MCP 1.0.28. That run published no package and did not satisfy A03's
published-only recording prerequisite. The [follow-up](AE-01a.md) records the release and current
consumption proof separately; this receipt preserves the original experiment.

The implementation also needed normal C# import/generic corrections, a build copy for shared
browser assets during `dotnet run`, and correct PowerShell decoding of ProblemDetails responses.
An initial deletion assertion expected lifecycle rejection but encountered the declared access
boundary first; the final assertion records the actual anonymous HTTP contract.

| Retained failed run | Cause |
|---|---|
| `2a3afc529a79466088078fe0d7f5c6de` | Generic static member qualification and provenance extension import |
| `0130c2ab28704149993b2f1765fe9f0e` | Missing Save extension import |
| `d4d4360cca0e4260b49adb591862615e` | Published Core rejected the ordinary foundation identity |
| `f18936a7997a4832aafc5dca0c45b173` | Harness decoded a JSON error body as bytes |
| `e21323469796428789087fceb921b414` | Harness expected lifecycle rejection before the access boundary |

One local preparation attempt also used an unsupported PowerShell selection parameter; it was
corrected before preparing the package used in the proof. These are construction iterations,
not independent agent attempts. Intermediate successful runs with narrower checks are retained.

## Adoption work and limits

The consumer did more than reference a package. Count the complete adoption surface:

| Owner | Authored work |
|---|---|
| Foundation | Nine C# files covering shared Entity/state, policy/options/constants, module, and HTTP projection; package project; version ownership; README and technical guidance |
| Each consumer | Five C# files: host, business Entity, module, constants, and controller; project reference; SQLite/MCP configuration; its own HTML; launcher and README |
| Workspace | Shared JavaScript/CSS, build boundaries and asset copying, solution, local Core preparation, package/update verifier, and agent instructions |

The shared module binds policy once; consumer modules add purchasing or expense rules. The two
applications authored no provider registration and copied no spending-limit enforcement. This is
evidence of technical reuse. It does not establish reduced senior intervention or newcomer success.

There were no independent participants. Human acceptance/review minutes, comparative elapsed time,
model/harness benchmark metadata, tokens, cost, and productivity effects are unavailable. One coding
session constructed and checked the fixture; this receipt must not become an evaluation score.

Identity, tenancy, concurrent decisions, external SQL bypass, payments, supplier delivery, durable
jobs, and semantic search are outside this proof. The generated Code Mode TypeScript used a
hyphenated Entity name as an interface identifier; AE-03 must assess/fix that generator boundary
before advertising Code Mode. The verified MCP surface here is ordinary tool calls.

Proceed to AE-02's predeclared evolution tasks and AE-03's real caller/tenant boundaries on this
same baseline. Release the Core fix through the normal release process before public first use.
